# Off the Mode · revisit state

Save where things stand, so the next session can start from here with no chat history. Run it when the user types it or asks for it, and on your own once at the end of a reply that modified project files or concluded a decision: after that reply's last edit, however many files it touched, never after each file. It writes only `.offthemode/STATE.md`, `.offthemode/DECISIONS.md` and, in `.offthemode/CHECKLIST.md`, the points and the mark of the piece just worked on, and, where the project uses git, git keeps their earlier versions, so it saves without asking, with no plan to approve first. While another Off the Mode command is running, wait until it has finished. An agent that another session started leaves `.offthemode/` alone and reports back; the session that started it saves.

If no `.offthemode/` folder holding RULES.md is found here or in a folder above: when the user asked, say the project isn't set up yet and offer the offthemode command, which sets it up; run on its own, do nothing and say nothing.

Sources: this session so far and the files as they are now. Run on its own, work from what was changed, decided or corrected in this session since STATE.md was last saved, and skip git. When the user asked for it, and the project uses git, also read what changed since STATE.md was last saved: `git status`, and `git log --since="<the date on STATE.md's first line> 00:00"` (a bare date counts from the current time of day and misses that day's earlier commits). Files and git are fact; the chat says what was meant and decided.

Never write the same thing twice, so it can run as often as it needs to. STATE.md is updated in place, never added to: each fact, step, item and correction has one line, so update the line that already says it, even in other words, instead of adding another. Search DECISIONS.md before adding to it. Run twice in a row, it changes nothing the second time.

1. Keep the points of the piece this reply worked on. A point is one thing the user said must be true, from an ask or from a "this is wrong". Find the piece's item in `.offthemode/CHECKLIST.md` by search, never by reading the file whole. Under the item, keep one indented line per point: `  - <date> "<the user's words>" · check: <how it is checked> · <what the check showed, or open>`. Update the line that already holds a point. Never drop one unless the user took it back; when a new point contradicts a kept one, ask which stands and mark the other replaced. The mark: an open point or a "this is wrong" sets the item to [~], whatever its mark was, and lowers the header's verified count by one when the mark was [v]; once every point's check has passed, [~] becomes [x]. Only revisit-checklist sets [v]. Work that matches no item: keep its points the same way under one line for the piece, `- <date> · <the piece in a few words>`, in the section `## Asks outside the plan` (add it above `## Changes` when it is missing), and leave it to revisit-checklist to place it as an item. An ask with no point to keep, such as a rename or a typo, gets nothing. Make these edits in the same step as STATE.md's.
2. Update `.offthemode/STATE.md` in place, keeping its sections and, word for word, every line that is still true: present tense, no history, under 40 lines, the first line dated today. A fresh session with no chat must be able to start item 1 of Next from this file alone, so name the files, the commands and the done-check. List everything claimed but not proven as unverified, because the next session trusts this file.
3. Append a `.offthemode/DECISIONS.md` entry, in the file's own format, for each decision from these sources that DECISIONS.md doesn't hold yet, even in other words, with the user's own words as the reason where there are some. A decision that changes an earlier entry gets a new entry naming the one it changes; the earlier entry's text stays as it is, and when the new entry replaces it whole, its status becomes "superseded by D-###", as the file's header says. A choice that isn't clearly settled, including one the code shows but the chat never named, stays out: write it as a question under STATE.md's Waiting on me, and ask it in the reply.
4. Add each correction the user gave for the first time about how the work is done to STATE.md's Corrections seen once, dated, unless it is already there; one about what the product does or shows is a point, kept in step 1. A correction the user gave again after it was already on that list has now been given twice: propose where it goes, as From correction to rule in the p0-constitution guide sorts it (a line for RULES.md §Project specifics with its reason; taste, a line for PRODUCT.md §Feeling or `.offthemode/DESIGN.md`; a pasted prompt that misled, its fixed version; a written rule broken again, a check in RULES.md §Commands), and keep it on the list, marked proposed, until that line is added. Propose a fix for any RULES.md line that proved wrong or out of date. Nothing in this step is applied without the user's yes; list each proposal still waiting under STATE.md's Waiting on me, so a fresh session still has it.

When the user asked for it, reply in at most 8 lines: the points kept and the marks that moved; what changed in STATE.md, item 1 of Next first; the decisions added, by id; any question still open. When it ran on its own and changed STATE.md or DECISIONS.md, end the reply with one line, `STATE.md updated`, and ask any question or proposal this run added to Waiting on me; when it changed nothing, add nothing. If the three files already hold everything the steps above would write, change nothing, not even the date; say STATE.md was already up to date only when the user asked.
